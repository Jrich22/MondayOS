- The sourcing-session page branches on `provider.agentOperatesBrowser`. ManualProvider renders today's capture surface with
  NO change, asserted by an existing-behaviour test; Claude-operated renders the command center.
- 'The command center displays: role and req code, brief version, target shortlist size, sourcing status, reviewed, rejected,
  potential matches, finalists N/target, current search strategy, current focus when present, session elapsed time, and the
  live ranked working shortlist.'
- Every count links to the work it counts (ADR-014). No statistic renders as a dead number.
- The working shortlist updates live over SSE as Claude writes, without a page refresh. Tested.
- The Candidate Workspace visibly separates LIVE SOURCING (session-scoped working shortlists for active sessions) from the
  PERMANENT TALENT POOL (finalized Candidates only). A test asserts a working-shortlist person does NOT appear in the talent
  pool before finalization.
- '`Finalize Shortlist` is a human-only UI action. There is no MCP path to it and no automatic trigger on reaching the target.
  A test asserts reaching the target alone promotes nothing.'
- 'Finalization is TRANSACTIONAL: candidates, reqCandidates and the session commit in ONE store update. A test forces a mid-promotion
  failure and asserts NOTHING was written — no orphan Candidate, no half-built shortlist.'
- Finalization accepts EITHER the default top N by domain ranking (N = `req.shortlistTarget`, default 20, configurable per
  req) OR a recruiter-selected subset of working-shortlist entries. Both freeze their set at the moment finalization runs.
- Selection is human-controlled in the UI only. No MCP tool can invoke finalization in either form, and no automatic trigger
  exists — asserted by a test.
- 'A selected subset runs the IDENTICAL transaction as the top-N path: freeze, validate, duplicate resolution, build, single
  atomic commit. A test asserts a subset finalization with an ambiguous duplicate blocks and writes nothing, exactly as the
  top-N path does.'
- 'Unselected working-shortlist entries remain session-scoped evidence: they do not become Candidates, are not deleted, and
  are not rewritten. A test asserts the remaining entries are byte-identical after a subset finalization.'
- 'Finalizing a subset does not close the door: the recruiter may finalize again later from the remaining entries, and the
  second run applies the same duplicate detection against the by-then-updated pool.'
- A session may be completed with fewer than `shortlistTarget` candidates. Session history records how many were finalized
  against the target, so a session that promoted 3 of 20 reads as a deliberate outcome rather than an unfinished one.
- There is NO per-person promote shortcut anywhere in the UI or the domain. A test asserts the only path from a working-shortlist
  entry to a Candidate is the finalize transaction (ADR-018).
- Duplicate detection re-runs AT FINALIZE TIME against the current pool, not only against what Claude saw. Unresolved duplicates
  BLOCK the transaction and surface a per-entry choice; nothing is auto-merged (ADR-012).
- 'Existing people are reused: a matched entry creates a `ReqCandidate` only, and differing Candidate-level facts become a
  `CandidateEnrichment` proposal rather than an overwrite (ADR-013). A test asserts the existing `Candidate` is unchanged
  after finalization.'
- 'New people are created with `origin: "supervised-session"`; every promoted `ReqCandidate` carries `reqId`, `candidateId`,
  `briefVersion`, `sourcedInSessionId`, and its assessments, rationale, relevant experience and concerns.'
- Fit scores are recomputed by the domain at finalize time against the `briefVersion` each entry was assessed under; entries
  assessed against a stale version are surfaced to the recruiter rather than silently rescored (ADR-003, ADR-019).
- Finalization refuses an entry whose person is already on the req (`isAlreadyOnReq`), reporting it rather than creating a
  second evaluation.
- After finalization the promoted people appear in the permanent talent pool, entries are stamped with their promoted ids,
  and the working shortlist remains readable as historical session evidence.
- An abandoned or completed-without-finalizing session keeps its working shortlist and promotes nothing. Tested.
- Manual candidate entry is removed from the Claude-operated flow only; it is not deleted from the codebase and remains reachable
  under ManualProvider.
- 'Full validation green: sourcingBOT `vitest`, TypeScript strict, production build, MondayOS `pytest`, and Cue App tests
  with zero Cue changes.'
