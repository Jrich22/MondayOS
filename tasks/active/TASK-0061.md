acceptance_criteria:
- 'The `sourcingbot` MCP server is served from `sourcingbot-host` over stdio and exposes exactly thirteen tools: `list_open_reqs`,
  `get_brief`, `get_active_session`, `get_working_shortlist`, `find_candidates`, `record_search_iteration`, `record_review_progress`,
  `record_potential_match`, `set_current_focus`, `upsert_working_shortlist_entry`, `drop_working_shortlist_entry`, `report_target_reached`,
  `halt_session`.'
- NO `finalize_shortlist` tool exists, and no tool creates a `Candidate` or a `ReqCandidate`. A test asserts both — finalization
  is UI-only because it creates permanent records about real people (ADR-018).
- NO `start_session`, `resume_session`, or `complete_session` tool exists (ADR-017 unchanged), asserted by a test on the tool
  list.
- '`get_brief` returns the FULL canonical brief — requirements with weights, target and excluded companies and industries,
  keywords, locations, seniority, experience guidance, outreach angle, sourcing goals, `briefVersion` — plus the req''s `shortlistTarget`.
  Tested field by field.'
- '`WorkingShortlistEntry` is session-scoped: it lives on `SourcingSession.workingShortlist` and is never promoted to a `Candidate`
  by any MCP call. A test asserts that upserting entries leaves `candidates` and `reqCandidates` untouched.'
- '`upsert_working_shortlist_entry` has NO `fitScore` parameter (ADR-019). sourcingBOT computes the score from the supplied
  assessments and the brief''s weights via the existing `withFitScore`, and ADR-006''s cap still applies. A test asserts the
  parameter''s absence and that a supplied score is ignored.'
- Entries are scored against the `briefVersion` they were assessed under, not the current brief (ADR-003). A test covers an
  entry created against v3 while the brief has moved to v4.
- '`upsert_working_shortlist_entry` is idempotent per profile reference: a second call for the same profile updates the entry
  rather than creating a duplicate. Tested.'
- '`drop_working_shortlist_entry` removes a session-scoped entry only. A test asserts it can never delete a `Candidate` or
  `ReqCandidate`, so replacing a weaker contender has no permanent effect.'
- 'Duplicate matches are REFERENCED, never mutated: `find_candidates` returns pool matches and the entry stores `matchedCandidateId`
  plus a match confidence. A test asserts the referenced `Candidate` record is byte-identical before and after (ADR-012).'
- One profile per call. No batch entry tool exists, asserted by a test. `record_review_progress` is exempt and may batch,
  because counters carry no personal data — the no-batch rule protects against bulk capture of people.
- 'Rejected profiles produce counters ONLY: no `Candidate`, no `ReqCandidate`, no stored name or profile reference. A test
  asserts that recording 50 rejections adds no named record anywhere (ADR-018).'
- '`record_potential_match` is capped at 25 per session; beyond the cap the call succeeds and reports that the cap was reached
  rather than silently discarding. Tested at the boundary.'
- '`record_search_iteration` stores rationale, a filter summary and a result count on the session. It stores no profile data.'
- '`set_current_focus` is ephemeral display state and is not part of the session''s durable evidence.'
- Every MCP write requires a live session AND `operatorPresent()`; on expiry the write fails `operator_absent` AND the session
  auto-pauses. Tested at the 15-minute boundary (ADR-017).
- '`report_target_reached` records that Claude stopped and why; it does NOT change the shortlist, promote anything, or end
  the session.'
- '`halt_session` is NEVER refused for a live session — tested on in-progress, paused and already-halted sessions.'
- '`ClaudeChromeProvider` declares `agentOperatesBrowser: true` with its own supervision policy naming that Claude operates
  the browser, the operator is present throughout, every decision is the operator''s, the session stops on any platform warning,
  and the operator accepts the ToS risk (ADR-015). A test asserts the ToS line is present and that ManualProvider''s wording
  is NOT reused.'
- '`ClaudeChromeProvider` contains no browser control, navigation, URLs, CSS or DOM selectors, retry or pacing logic, and
  no credentials. A test greps the module and fails on any of these.'
- Session metrics (`reviewed`, `rejected`, `potentialMatches`, `workingShortlistSize`, `searchIterations`) are stored on the
  session and derived counts remain correct for legacy sessions with no metrics block.
- '`ManualProvider` remains fully functional and default; the manual capture path works with the MCP server absent. `PROHIBITED_CAPABILITIES`
  unchanged and `supportsCapability()` still false for every entry.'
- README documents registering the MCP server with Claude Code, `claude --chrome`, and the one-time Chrome native-host install.
- 'Full validation green: sourcingBOT `vitest`, TypeScript strict, production build, MondayOS `pytest`, and Cue App tests
  with zero Cue changes.'
