Final product resolutions for Cue App's Invite & RSVP increment (TASK-0023). These resolve the open product questions in DOC-0016 and extend DEC-0010; they do not rewrite DEC-0010's approved rules and do not authorize implementation.

1. Prototype guest surface

The guest RSVP surface is intentionally a same-browser "Respond as guest" preview for this increment. It validates the guest journey but is not a production-public or cross-device experience. The UI and documentation must state this limitation clearly.

2. Sensitive prototype data

Dietary and accessibility fields may be exercised only with synthetic/demo data in this localStorage prototype. Cue must not encourage entry of real sensitive guest information in this increment. Production privacy, encryption, retention, access control, and consent decisions are hard prerequisites before using these fields with real guests.

3. Invitation model

Use a separate lightweight Invitation entity rather than placing invitation lifecycle fields directly on Guest. The Invitation references canonical eventId and guestId and owns invitation-specific concerns: token identifier/version; lifecycle status; issued, delivered, revoked, rotated, responded, and updated timestamps as applicable; plus-one allowance; and delivery state or reference. Guest remains the canonical source for RSVP response, attendance, preferences, and actual plus-one count. Do not duplicate Guest or Event data inside Invitation.

4. Plus-one allowance

Use a per-invitation nonnegative integer allowance with a default of 0. The organizer must explicitly grant additional plus-ones. The guest's accepted plus-one count cannot exceed that allowance. Capacity calculations use the accepted count, not the allowance. Do not add an event-level plus-one default in this increment.

5. Waitlist ordering

Record response time and present waitlisted guests in FIFO order as the recommended promotion sequence. Promotion remains an explicit organizer decision; Cue does not automatically promote a guest or prevent the organizer from selecting another waitlisted guest.

6. Token lifecycle

Rotating or revoking an invitation token invalidates all prior links immediately within the prototype model. The organizer must be able to see whether an invitation is active, revoked, or rotated, and when the latest token was issued. Tokens contain no PII and are explicitly not production-secure without a backend-held secret.

These resolutions must be used together with DEC-0010 when MondayOS later translates the Invite & RSVP increment into engineering work.
