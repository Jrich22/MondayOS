The following rules resolve the product questions surfaced in DOC-0015 and govern Cue App's Event Planning increment.

1. Planning ownership

Introduce a lightweight WorkspaceMember concept behind the existing mock-session seam. WorkspaceMember represents an application user who can own planning responsibilities. It is distinct from Person, which remains a persistent relationship record. This does not introduce production authentication or full RBAC.

2. Operational readiness

Readiness is initially expressed through explainable category states:

- Complete
- Attention Needed
- Blocked
- Not Applicable

Every state must show its contributing evidence and required next action. Do not introduce a weighted readiness percentage until weighting has been validated with customers and real event usage. Readiness may use only capabilities Cue currently supports.

3. Capacity and RSVP demand

Venue or event capacity is a hard operational constraint. Invited, confirmed, waitlisted, and projected attendance counts are demand signals. Keep these concepts separate. Cue should warn when confirmed or projected attendance threatens or exceeds capacity without redefining capacity as an RSVP count.

4. Planning-to-execution handoff

Event Planning owns pre-event readiness, milestones, responsibilities, risks, and setup decisions. Roll Call and Check-In consume the canonical event and guest state when the event enters its operational phase. Completed execution modules must not maintain a separate copy of planning state.

5. Templates

Event templates are organization-visible and versioned. Published template versions are immutable so existing events retain their historical configuration. Until production RBAC exists, template editing is limited to the current workspace owner through the existing user seam, and all changes retain provenance.

6. Guided setup

The guided Event Planning setup augments the existing create-event flow; it does not replace or rebuild it. Existing event fields and creation logic remain canonical. The setup experience progressively gathers planning information and transitions the user into the ongoing planning workspace.

7. Venue boundary

Event Planning may introduce lightweight reusable Venue and Room primitives and event-specific assignments. Detailed venue logistics, layouts, vendor operations, and operational checklists remain outside this increment and belong to the future Venue/Vendor capability represented by TASK-0024.

These rules extend DEC-0008 and DOC-0015. They do not authorize implementation. MondayOS must use them when it later translates the approved product increment into engineering work.
