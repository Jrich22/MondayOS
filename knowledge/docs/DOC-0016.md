Records the approved product shape for the Invite & RSVP increment (decision DEC-0010), scoped under the Invite & RSVP epic (TASK-0023). This is a non-implementation product definition: it does not authorize code, an engineering brief, or implementation.

Roadmap context: the Event Planning foundation is delivered (TASK-0049, slice 1), satisfying the precondition in DEC-0008. Organization-wide planning templates and reusable venue/room primitives remain deferred under TASK-0020 and do not block this increment.

## Customer outcome

An organizer can invite guests via an opaque per-invitation link, guests respond (confirmed / tentative / declined) with an allowed anonymous plus-one count and optional dietary/accessibility notes, and the organizer sees the response funnel, pending responses, capacity-vs-demand, and actionable waitlist decisions — all as a browser-local prototype, with no backend, production auth, or real email.

## Approved operating rules

Captured verbatim in decision **DEC-0010** (10 rules: MVP architecture; guest access via opaque token; simulated delivery; anonymous plus-ones; RSVP responses & privacy; capacity & waitlist; editing & withdrawal; organizer monitoring & reminders; guest experience; scope boundaries).

## Dependencies (reuse-first; existing capabilities this builds on)

- Guest / attendee model (TASK-0035): `Guest.attendance.rsvp` (invited/confirmed/tentative/declined/waitlisted), `plusOnes`, `waitlisted`; `preferences.dietary`/`accessibility`; `communication.invitationSent`/`reminderSent` — the RSVP fields already exist.
- Signed-credential precedent (TASK-0045, `lib/qr`): client-side signed token `hash36(eventId + guestId + salt)` — no PII, spoof-resistant, no server secret. The invitation token follows this precedent.
- Communications Center (TASK-0043, `lib/comms`): existing `invitations` and `rsvp-reminders` campaign kinds and audiences for simulated delivery and manual reminders.
- Event Planning foundation (TASK-0049): canonical event/capacity model and `capacityDemand` (capacity kept separate from demand, DEC-0009 §3) for the waitlist rule.
- Event workspace / Event Detail (TASK-0034) and Mission Control (TASK-0042) for the organizer response funnel and waitlist surfacing.
- Event branding/theme (`EventBranding.theme`, `lib/branding`) for the guest surface — no new branding system.

## Consistency with existing decisions

Consistent with DEC-0003 (no payments/ticketing/production auth), DEC-0005 (guest counts model RSVPs, never tickets), and DEC-0009 §3 (capacity is a hard constraint separate from demand). No contradictions with approved decisions were found.

## Contradictions / material tensions to resolve

1. **"Guest-facing" vs single-device localStorage.** A browser-local prototype (no backend) cannot share state across devices, so a guest opening a link on their own phone would not see the operator's data. The "guest response surface" is effectively an operator-side/same-browser preview this increment. This is acknowledged by rule 1 (documented prototype) but must be designed explicitly (see questions).
2. **"Signed credential" without a server secret.** Following the `lib/qr` precedent, the token is a client-side hash signature — spoof-resistant but NOT cryptographically secure (the salt ships in the client). Acceptable for a documented prototype; production token security is deferred.
3. **Revocation/rotation needs invitation state.** Rule 2 (revocation/rotation) and rule 7 ("invitation remains active") require an invitation lifecycle state (active/revoked, token version) that does not exist yet. Needs a model decision (extend Guest vs a small Invitation record).
4. **Per-invitation plus-one allowance is a new field.** Rule 4 constrains plus-ones by "the invitation's allowance," but only an actual `plusOnes` count exists today — no allowance/max. A default and storage location are undecided.

## Missing decisions (needed before engineering execution)

- Invitation model: is the token bound to the existing `Guest` record (as `lib/qr` binds to guestId) or a separate lightweight Invitation entity? Where do token version, revoked flag, and plus-one allowance live?
- Default plus-one allowance (event-level default vs per-invitation), and how it interacts with `EventCapacity`.
- Waitlist ordering for organizer promotion (FIFO by response time? manual only?). Rule 8 says promotion is explicit but does not specify ordering.
- How the guest experience is exercised in a single-device prototype (a same-browser "respond as guest" preview route?).
- Token rotation semantics: does rotating a token invalidate prior links immediately, and how is that surfaced to the organizer?

## Unresolved product questions (for human approval)

- Confirm the guest surface is a same-browser preview for this increment (not a real remote guest device), and that this satisfies the customer outcome for validation purposes.
- Confirm dietary/accessibility data stored unencrypted in localStorage is acceptable for the prototype, with production privacy controls as a hard prerequisite for any real release.
- Confirm the invitation is modeled on the existing Guest record (reuse) unless a separate Invitation entity is explicitly preferred.
- Confirm a default plus-one allowance (e.g., inherit from the event, default 0/1) so capacity math is well-defined.
