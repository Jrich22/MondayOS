Records the approved product shape for the Invite & RSVP increment (decision DEC-0010), scoped under the Invite & RSVP epic (TASK-0023). This is a non-implementation product definition: it does not authorize code, an engineering brief, or implementation.

Roadmap context: the Event Planning foundation is delivered (TASK-0049, slice 1), satisfying the precondition in DEC-0008. Organization-wide planning templates and reusable venue/room primitives remain deferred under TASK-0020 and do not block this increment.

## Customer outcome

An organizer can invite guests via an opaque per-invitation link, guests respond (confirmed / tentative / declined) with an allowed anonymous plus-one count and optional dietary/accessibility notes, and the organizer sees the response funnel, pending responses, capacity-vs-demand, and actionable waitlist decisions — all as a browser-local prototype, with no backend, production auth, or real email.

## Approved operating rules

Captured verbatim in decision **DEC-0010** (10 rules: MVP architecture; guest access via opaque token; simulated delivery; anonymous plus-ones; RSVP responses & privacy; capacity & waitlist; editing & withdrawal; organizer monitoring & reminders; guest experience; scope boundaries).

## Dependencies (reuse-first; existing capabilities this builds on)

- Guest / attendee model (TASK-0035): `Guest.attendance.rsvp` (invited/confirmed/tentative/declined/waitlisted), `plusOnes`, `waitlisted`; `preferences.dietary`/`accessibility`; `communication.invitationSent`/`reminderSent` — the RSVP fields already exist.
- Signed-credential precedent (TASK-0045, `lib/qr`): client-side signed token `hash36(eventId + guestId + salt)` — no PII, spoof-resistant, no server secret. The invitation token follows this precedent.
- Communications Center (TASK-0043, `lib/comms`): existing `invitations` and `rsvp-reminders` campaign kinds and audiences for simulated delivery and manual reminders.
- Event Planning foundation (TASK-0049): canonical event/capacity model and `capacityDemand` (capacity kept separate from demand, DEC-0009 §3) for the waitlist rule.
- Event workspace / Event Detail (TASK-0034) and Mission Control (TASK-0042) for the organizer response funnel and waitlist surfacing.
- Event branding/theme (`EventBranding.theme`, `lib/branding`) for the guest surface — no new branding system.

## Consistency with existing decisions

Consistent with DEC-0003 (no payments/ticketing/production auth), DEC-0005 (guest counts model RSVPs, never tickets), and DEC-0009 §3 (capacity is a hard constraint separate from demand). No contradictions with approved decisions were found.

## Product resolutions (RESOLVED by DEC-0011)

The material tensions and open product questions below are retained for history and are **all resolved by `DEC-0011` (Cue Invite & RSVP — product resolutions and prototype boundaries)**. No implementation-gating product question remains, and resolving them introduced no new contradiction with the approved decisions.

1. **Prototype guest surface (Q: guest-facing vs single-device localStorage).**
   **Resolved (DEC-0011 §1):** the guest surface is intentionally a same-browser "Respond as guest" preview this increment — not production-public or cross-device. The UI and docs must state this clearly.
2. **Sensitive prototype data (Q: dietary/accessibility in unencrypted localStorage).**
   **Resolved (DEC-0011 §2):** these fields may be exercised only with synthetic/demo data; Cue must not encourage real sensitive input. Production privacy/encryption/retention/access/consent are hard prerequisites before real use.
3. **Invitation model (Q: extend Guest vs a separate entity; where token/revocation/allowance live).**
   **Resolved (DEC-0011 §3):** use a **separate lightweight Invitation entity** referencing canonical `eventId`/`guestId`, owning token id/version, lifecycle status, issued/delivered/revoked/rotated/responded/updated timestamps, plus-one allowance, and delivery state. Guest stays canonical for RSVP response, attendance, preferences, and actual plus-one count; no Guest/Event data is duplicated in Invitation.
4. **Plus-one allowance (Q: default and storage).**
   **Resolved (DEC-0011 §4):** a **per-invitation nonnegative integer allowance, default 0**; the organizer explicitly grants more; accepted plus-ones cannot exceed it. **Capacity uses the accepted count, not the allowance** (reuses `capacityDemand`, DEC-0009 §3). No event-level default in this increment.
5. **Waitlist ordering (Q: promotion sequence).**
   **Resolved (DEC-0011 §5):** record response time and present waitlisted guests in **FIFO order** as the recommended promotion sequence; promotion stays an explicit organizer decision (no auto-promotion; the organizer may pick another waitlisted guest).
6. **Token lifecycle / security (Q: rotation semantics; client-side signature).**
   **Resolved (DEC-0011 §6):** rotating or revoking a token **invalidates all prior links immediately** in the prototype model; the organizer sees active/revoked/rotated status and the latest-issued time. Tokens carry no PII and are explicitly **not production-secure** without a backend-held secret (documented prototype limitation).
