Records the approved product shape for the Event Planning increment (decision DEC-0008), scoped under the Event Workspace epic (TASK-0020). This is a non-implementation product definition: it does not authorize code, redesign completed modules, or begin implementation.

## Approved product decisions

1. Event Planning remains Cue App's active next roadmap increment.
2. The experience is a guided setup that transitions into an ongoing planning workspace.
3. Readiness must be explainable and based only on capabilities Cue currently supports.
4. Templates are reusable organization-wide assets.
5. Authenticated Cue users own planning responsibilities; People remain relationship records.
6. Venue scope is lightweight reusable venues and rooms, not detailed venue logistics.
7. Initial scope includes multi-day structure, milestones, responsibilities, risks, capacity, templates, and operational readiness.
8. AI provides suggestions only; all changes require review before application.
9. Invite & RSVP remains the next high-priority lifecycle gap after the Event Planning foundation.

## Initial scope

Multi-day structure, milestones, responsibilities, risks, capacity, templates, and operational readiness — delivered as an extension of the existing event model and completed event workspace, not a rebuild.

## Boundaries (from DEC-0008)

- Extend the existing event model and completed event workspace; do not redesign completed modules.
- Begin with a guided setup that transitions into an ongoing planning workspace plus an operational-readiness model.
- Do not absorb full Registration, Session Management, Speaker Management, Budgeting, or detailed Venue Management into this increment.
- AI may suggest plans, milestones, and risks, but users must review and approve changes before they apply.

## Dependencies (existing capabilities this builds on)

- Event workspace foundation and create-event flow (TASK-0033, TASK-0034, TASK-0041; event model per DEC-0006) — extended, not rebuilt.
- Guest / attendee model (TASK-0035) and Relationship Intelligence / People records (TASK-0044) — provide capacity and responsibility context; People remain relationship records, not owners.
- Multi-Organization Architecture (TASK-0038) — enables templates as organization-wide reusable assets.
- Communications Center (TASK-0043) and Roll Call / Check-In (TASK-0040, TASK-0045) — current capabilities an explainable readiness model may reference.
- Mock session identity (`currentUser`; auth placeholder per DEC-0003) — the only present "authenticated user" seam for ownership.

## Architectural conflicts / tensions to resolve

1. **Ownership vs. deferred auth.** "Authenticated Cue users own planning responsibilities," but production auth is deferred (DEC-0003) — only a mock `currentUser` exists. Ownership must bind to that placeholder identity seam until real auth lands; this increment must not build a user/RBAC system.
2. **People are relationship records, not users.** Responsibilities are owned by authenticated users, not People. The model must keep owner (user) distinct from People (guests/relationships) to avoid conflation.
3. **Readiness constrained to current capabilities.** The readiness model may derive only from capabilities Cue already supports (guests, comms, roll call, check-in), not from unbuilt Registration/Sessions/Speakers. Signals must be explainable and must not fabricate coverage from future features.
4. **Multi-day extends the event container.** DEC-0006 makes the event the container; multi-day structure, milestones, and capacity must extend `CueEvent`/`eventId` references rather than introduce a parallel model.
5. **Templates as a new org-wide entity.** Requires template storage spanning organizations (supported by TASK-0038) but with no edit-permission model yet (no RBAC).
6. **Venue boundary.** Lightweight reusable venues/rooms must not drift into the deferred Vendor/Venue Tracker epic (TASK-0024) detailed logistics.

## Product questions (RESOLVED by DEC-0009)

The questions below are retained for historical visibility. All are **resolved by
`DEC-0009` (Cue Event Planning — operating semantics and boundaries)**; concise
answers follow each. See DEC-0009 for the full operating rules.

- **Q:** How is an "authenticated Cue user" represented for ownership while production auth is deferred (DEC-0003) — use the mock session identity now, behind a defined seam for real auth?
  **A (DEC-0009 §1):** Introduce a lightweight `WorkspaceMember` behind the existing mock-session seam to own planning responsibilities — distinct from `Person` (relationship record). No production auth or full RBAC.
- **Q:** What is the concrete, explainable definition of "operational readiness," and exactly which current capabilities feed each readiness signal?
  **A (DEC-0009 §2):** Explainable category states — Complete / Attention Needed / Blocked / Not Applicable — each showing contributing evidence and required next action. No weighted percentage until validated; readiness uses only capabilities Cue currently supports.
- **Q:** How does capacity relate to existing RSVP-based guest counts (DEC-0005: counts model RSVPs, never tickets)?
  **A (DEC-0009 §3):** Capacity is a hard operational constraint; invited/confirmed/waitlisted/projected are demand signals kept separate. Warn when confirmed/projected attendance threatens or exceeds capacity, without redefining capacity as an RSVP count.
- **Q:** Do Event Planning milestones / run-of-show overlap with existing Roll Call and execution surfaces, and where is the handoff?
  **A (DEC-0009 §4):** Event Planning owns pre-event readiness, milestones, responsibilities, risks, setup. Roll Call and Check-In consume canonical event/guest state in the operational phase; execution modules keep no separate copy of planning state.
- **Q:** Are organization-wide templates versioned, and who may edit them given there is no RBAC yet?
  **A (DEC-0009 §5):** Templates are organization-visible and versioned; published versions are immutable. Until RBAC exists, editing is limited to the current workspace owner via the user seam, with provenance retained.
- **Q:** Does the guided setup replace or augment the current create-event flow (TASK-0033)?
  **A (DEC-0009 §6):** It augments — it does not replace or rebuild. Existing event fields and creation logic remain canonical; setup progressively gathers planning info and transitions into the ongoing planning workspace.
